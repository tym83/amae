# Amae

Amae — эзотерический язык программирования, в котором вычисление
происходит не внутри душ, а между ними. Программа — это несколько душ, которые
живут бок о бок. Добраться друг до друга они могут только на встрече; они
доверяют и боятся, отдают сердце, ранят и прощают, а всё, что они сказали друг
другу, остаётся с ними.

Язык Тьюринг-полон, и доказательство держится не на памяти, которая
выцветает, а на доверии: машина со счётчиками работает на том, насколько одна
душа доверяет другой.

Имя — японское *amae* (甘え): спокойная уверенность, что близкий примет тебя
и позаботится о тебе. На этом чувстве держится весь язык.

```
written by "amae"

soul alice
    meet bob
    give heart to bob
    knowingly confide bob "the thing I never told anyone"
    hear bob into answer
    say "alice heard: " + answer
end

soul bob
    meet alice
    hear alice into secret
    knowingly wound alice
    tell alice "I know"
end
```

## Запуск

Amae — компилируемый язык. Его компилятор написан на Amae и выдаёт C,
который любой компилятор C11 собирает вместе со средой исполнения из
`runtime/`.

```
make                                      # the compiler, from its seed in boot/tc.c
bin/tc examples/hello.amae             # compile a program
./hello
./courtship --feelings                    # print every relationship at the end
make bootstrap                            # the compiler compiles itself
make test                                 # every recorded program, compiled and run
python3 -m unittest discover -s tests     # what the programs mean
```

Нужны компилятор C и make; Python пригодится только для тестов и для связки
с Kubernetes.

Каждый запуск записывается в `~/.amae/history.json` (или в файл, указанный
в `AMAE_HISTORY`) ещё до того, как начнётся, поэтому одна и та же программа
никогда не выполняется в первый раз дважды.

## Язык

Программа — это перечень душ, каждая из которых записана как
`soul <name>` … `end`; родов душ, записанных как `kind <name>` … `end`, из
которых во время работы программы рождаются новые души; и ритуалов, записанных
как `ritual <name> <a>, <b>` … `end`, которые может совершить любая душа.
В каждом раунде всякая душа, которая ещё жива, делает один шаг, в том порядке,
в каком души записаны; душа, с которой начинается раунд, сдвигается с каждым
прошлым запуском программы.

Внутри души есть целые числа и дроби, строки, списки и словари, JSON в обе
стороны, файлы, команды, которые душа просит мир выполнить или слушает,
время и случай. Ошибку можно пережить конструкцией `endure … when it hurts as
pain`, а чужие файлы изучить через `learn`. Таблицы ниже — о словах между
душами, а все слова языка собраны в [справочнике](docs/reference.ru.md).

### Что душа может сказать самой себе

| Инструкция | Смысл |
|---|---|
| `let x = expr`, `x = expr` | запомнить значение |
| `say expr` | сказать миру (в стандартный вывод) |
| `if expr` … `else` … `end` | |
| `while expr` … `end` | |
| `mark name`, `return to name` | дать мгновению имя и потом к нему вернуться |
| `first time` … `end` | выполняется только при самом первом запуске программы |
| `wait` | пропустить шаг |
| `recall x y …` | снова вспомнить об этом, чтобы воспоминания не выцветали дальше |
| `note key = expr` | записать в заметку; заметки никогда не выцветают |
| `bring k named expr` | привести в мир новую душу рода `k` |
| `wait for silence` | ждать, пока ни у кого больше не останется дел |
| `perform r with a, b into x` | совершить ритуал; `with` и `into` необязательны |
| `give back expr` | завершить ритуал и вернуть то, ради чего его совершали |
| `hear world into x` | прочитать строку со стандартного ввода; когда ввод кончается, `x` становится `0` |
| `goodbye` | завершить эту душу |

### Что говорится между двумя душами

| Инструкция | Смысл |
|---|---|
| `meet b` | встреча: обе души должны ждать друг друга; срока ожидания нет |
| `meet anyone as x` | встретить того, кто пришёл тебя искать, и узнать его имя |
| `tell b expr` | передать значение; завершается, только когда `b` слушает |
| `hear b into x`, `hear anyone into x [from who]` | слушать; `from` узнаёт, кто говорил |
| `knowingly confide b expr` | доверить тайну; можно только тому, кому отдал сердце |
| `warm to b`, `cool to b` | доверять `b` на ступень больше или меньше |
| `promise b` | обязательство растёт |
| `give heart to b` | необратимо; теперь `b` можно доверять тайны, и рана от `b` больше не закрывает тебя |
| `knowingly wound b` | `b` теряет к тебе всё расчётное доверие и половину близости и получает шрам |
| `forgive b` | открыть дверь, которую закрыла рана от `b`; шрам остаётся |
| `knowingly leave b` | необратимо; всё, что каждый из вас слышал, становится шрамами |

Везде, где называют душу, её можно назвать вычисленным словом через
`soul named expr`: `tell soul named who "yes"`.

### Выражения

Числа, строки, `+ - * / %`, сравнения, `and`, `or`, `not` и то, что душа
знает о своих отношениях: `trust b`, `intimacy b`, `passion b`,
`commitment b`, `afraid of b`, `bond with b`, `scars of b`, `scar n of b`, а
также `runs` — сколько раз эта программа запускалась прежде. У слов есть
`length of x` и `part i j of x` — буквы с `i`-й по `j`-ю, считая с единицы.
Строка — это ещё и список слов: `words of x`, `word i of x`, `place of w in x`
(0, если `w` там нет) и `number of x`. Своё имя душа знает как `me`, а свои
заметки читает через `note key`.

### Ритуалы

Ритуал совершает та душа, которая его вызывает: ему достаются её заметки и
отношения, но память у него своя, поэтому он может совершать самого себя.

```
ritual move n, from_peg, to_peg, spare
    if n == 0
        give back 0
    end
    perform move with n - 1, from_peg, spare, to_peg
    say "disk " + n + ": " + from_peg + " -> " + to_peg
    perform move with n - 1, spare, to_peg, from_peg
end
```

Ритуал совершается на одном дыхании: воспоминания, которые душа оставила за
его порогом, пока он длится, не выцветают. Его собственные воспоминания
выцветают, как и все прочие, поэтому счётчик, к которому длинный цикл
обращается лишь изредка, стоит вспоминать на каждом витке.

## Как устроены чувства

**Встреча.** Душе, с которой ты ни разу не встречался, ничего нельзя сказать.
При первой встрече страсть становится равной 3, если обе души пришли в одном
и том же раунде (с первого взгляда), и 1 в противном случае. Каждая следующая
встреча прибавляет 1; за каждые 50 шагов без встречи страсть остывает на 1.

**Слова, на которые ответили.** Близость растёт с обеих сторон, только когда
на сообщение отвечают. Сообщения без ответа усиливают давление. Когда давление
превышает близость слушающего больше чем на два, слушающий пугается:
несколько шагов до него ничего не доходит от говорящего, а его страсть падает.

**Два рода доверия.** Расчётное доверие (`warm to`, `cool to`) зарабатывают и
отсчитывают, и одна-единственная рана сбрасывает его в ноль и закрывает дверь,
пока раненая душа не простит. Дар (`give heart to`) нельзя ни заработать, ни
забрать назад: вместе с сердцем он отдаёт и нож. Душу, отдавшую сердце, всё
равно можно ранить и оставить ей шрам, но она остаётся открытой, и только дар
позволяет доверять тайны.

**Кто мы друг другу.** `bond with b` называет отношения по треугольнику
Стернберга: близость, страсть и обязательство, и каждая из них идёт в счёт,
когда доходит до 3. Получается одно из восьми: пока ничего (`nothing yet`),
симпатия (`liking`), влюблённость (`infatuation`), пустая любовь
(`empty love`), романтическая любовь (`romantic love`), дружеская любовь
(`companionate love`), безрассудная любовь (`fatuous love`) и совершенная
любовь (`consummate love`), — и меняется это вместе с отношениями.

**Выцветающая память.** Значение, на которое никто не смотрит, за каждые 50
шагов забвения теряет одну цифру или один символ с конца. Если снова на него
взглянуть, сохранится уже выцветшая версия. Ожидание тоже считается временем,
так что, пока душа ждёт, её воспоминания выцветают.

**Шрамы.** Шрамы никогда не выцветают, и их можно только читать. Когда одна
душа уходит, другая продолжает ждать, и программа завершается списком тех,
кто всё ещё ждёт.

**Коды выхода.** 0, когда каждая душа дошла до конца; 1 при ошибке; 2, когда
оставшиеся души вечно ждут друг друга; 4, когда кончается терпение
(`--patience=N` раундов).

## Тьюринг-полнота

`tools/minsky.py` компилирует любую счётчиковую машину Минского в Amae.
Каждый счётчик становится душой, его значение — это доверие машины к нему,
`warm to` прибавляет единицу, `cool to` отнимает, а `trust c == 0` проверяет
на ноль. Минский показал, что двух счётчиков хватает, чтобы смоделировать
любую машину Тьюринга. Тесты компилируют случайные машины с двумя счётчиками
и сверяют каждый результат с эталонным симулятором.

```
python3 tools/minsky.py examples/multiply.minsky > examples/multiply.amae
bin/tc examples/multiply.amae && ./multiply   # c = 42
```

## Операторы

Программа на Amae присматривает за кластером Kubernetes через `kubectl`, и
между ними ничего нет. `lib/kube.amae` спрашивает кластер (в контексте из
`KUBE_CONTEXT`) и читает его ответ как JSON; `listen to world` на
`kubectl get … --watch-only` будит программу всякий раз, когда что-то
меняется. Душа, ожидающая мир, не застряла — просто мир нетороплив, и
программа живёт до тех пор, пока кластер с ней разговаривает, а с
`--patience=0` — без всякого предела.

`kube/parting.amae` — первый оператор, написанный на Amae. Нода с
аннотацией `amaenetes.io/leaving: "true"` бережно уходит из кластера:
перестаёт принимать новых и отпускает свои поды по одному, следующий — только
когда предыдущего уже нет, а его владелец поднял замену. Поду, который не
принадлежит ни одному контроллеру, неоткуда вернуться, поэтому нода его не
выгоняет, а ждёт. Опустевшую ноду помечают `amaenetes.io/left: "true"`.

Оператор следит за нодами и подами и смотрит на кластер при каждом изменении
и раз в несколько секунд. Без `KUBE_CONTEXT` он слышит кластер строками со
стандартного ввода и говорит, что сделал бы, — так его проверяют.

```
bin/tc kube/parting.amae
KUBE_CONTEXT=<ctx> ./parting --patience=0
kubectl --context <ctx> annotate node worker-3 amaenetes.io/leaving=true
```

Если запустить его рядом с планировщиком, весь круг замыкается на Amae:
оператор отпускает под, а планировщик находит его замене новый дом. Вот как
уходит нода кластера из трёх нод, пока оба работают в нём подами; у голого
пода `db` нет владельца, который вернул бы его, поэтому нода остаётся и
объясняет почему:

```
08:03:26 > cordon cw2gd
08:03:26 cw2gd is leaving and takes no one new
08:03:26 > evict cozy-cilium/cilium-operator-697848cbf7-2bjzl
08:03:31 > evict cozy-monitoring/metrics-server-5c5559f4c6-krjgz
08:03:57 > evict kube-system/coredns-77b6676859-bmbz2
08:04:34 > evict scarcity/crowd-5bb975f679-5564z
08:04:44 > evict scarcity/crowd-5bb975f679-76b5c
08:04:54 cw2gd cannot leave: its last pod has nowhere to come back from
```

`kube/counsel.amae` хранит то, что рабочая нагрузка и нода прожили вместе,
в объекте `Relationship` (`amae.io/v1`, в неймспейсе нагрузки, с именем из
нагрузки и ноды), и рассказывает, как у них дела, так, как Джон Готтман
рассказывает о парах. Каждый взгляд на кластер — мгновение их общей жизни:
готовый под — шаг навстречу, перезапуск — критика, перезапуск из-за памяти —
презрение, под, от которого отказался kubelet, — оборона, под или нода, которые
не отвечают, — игнорирование. Мгновения выцветают, на одну сотую за взгляд,
так что важна недавняя жизнь двоих. Если на каждое плохое мгновение приходится
пять хороших или больше, отношения устойчивы, если меньше — под угрозой, а если
плохих больше, чем хороших, — рушатся. Шрамы, каждый перезапуск и каждый отказ,
не выцветают никогда. Накопленные итоги отношений сохраняются в объектах
между перезапусками counsel.

Liveness- и readiness-пробы — запросы внимания (bids): успешная проба — ответ
**towards** (навстречу), неудачная — **away** (отвернуться), а завершение
контейнера из-за неудачной liveness-пробы — **against** (против). Число попыток
оценивается для каждого контейнера как прошедшие секунды / `periodSeconds`
(по умолчанию 10). Для нового пода отсчёт идёт от `status.startTime`, но не
дольше одного интервала наблюдения. Startup-пробы не учитываются. Два списка
Events за взгляд дают прирост счётчиков `Unhealthy` и `Killing`; учитываются
только отказы liveness/readiness и завершения из-за liveness. Время наблюдений
и предыдущие счётчики Events хранятся в заметках, сбрасываются при перезапуске,
а исчезнувшие поды и Events удаляются из них. Первый взгляд только запоминает
исходные счётчики Events, не добавляя away или against. После этого новый Event
учитывается целиком.

Поля статуса `bids`, `towards`, `away`, `against` выцветают с множителем 0.99
за взгляд и округляются до сотых, как мгновения. `towards` — оценка попыток
минус away и against, не ниже нуля. `turning` — целый процент ответов навстречу
(отсутствует без bids), показанный в колонке **Towards**. Когда выцветшая сумма
`bids` достигает 20, менее 33% означает failing, менее 86% — не лучше at risk;
иначе здоровье определяет соотношение 5:1. Это ориентиры Готтмана: около 86%
у оставшихся вместе пар и 33% у расставшихся. Away и against записываются
в историю; against не добавляет презрения или шрамов.

```
kubectl --context <ctx> get relationships -A
```

Аннотация пода `amaenetes.io/attachment` задаёт поведение при потере связи
с нодой: её условие Ready больше не True (NotReady или Unknown).

- `secure` (по умолчанию, в том числе для неизвестных значений) ждёт 60 секунд,
  затем спокойно уходит через eviction с событием Normal `Separated`:
  `secure: <node> out of touch for <n>s, moving on`. Возвращение ноды до этого
  срока не добавляет шрама.
- `anxious` уходит через 15 секунд с событием Warning `Separated`:
  `anxious: <node> out of touch for <n>s`.
- `avoidant` сам не уходит. Если нода вернулась после более чем 15 секунд
  молчания, отношения её и нагрузки получают один постоянный шрам (его читает
  `distrust` планировщика) и строку истории:
  `<pod> kept its distance: <node> went silent for <n>s`. Следующие наблюдения
  не повторяют шрам. Собственное выселение Kubernetes по taint продолжает действовать.

Пороги в секундах задаются через `COUNSEL_SECURE_AFTER` (60),
`COUNSEL_ANXIOUS_AFTER` (15) и `COUNSEL_AVOIDANT_AFTER` (15). Выселение при разлуке
работает независимо от `COUNSEL_DIVORCE`, только для подов с владельцем;
завершающиеся поды пропускаются. Бюджет прерываний может отказать в выселении —
тогда следующая попытка будет при следующем наблюдении. Разлука отсчитывается
с первого наблюдения потери готовности; время хранится в заметках по UID пода,
очищается при возвращении ноды, удаляется для исчезнувших подов и сбрасывается
при перезапуске counsel.

#### Фазы

Фазы Хелен Фишер описывают жизнь каждого пода с нодой. Pending — это
**lust**: под хочет дом, но ещё не живёт в нём, поэтому counsel пропускает его
отношения с нодой. Работающий под находится в **attraction**, пока не пробудет
непрерывно Ready в течение `COUNSEL_ATTACHMENT_AFTER` секунд (по умолчанию
**300**), затем наступает **attachment**. Counsel хранит часы Ready по UID пода
в notes, при первом наблюдении берёт `Ready.lastTransitionTime` (или текущее
время, если отметки нет) и сбрасывает отсчёт при потере Ready или рестарте.
Исчезнувшие UID удаляются. Эти фазы не зависят от политики разлуки
secure/anxious/avoidant.

Поле статуса отношений `phase`, показанное в колонке **Phase**, берётся у самого
молодого по времени создания пода партнёра на этой ноде. В attraction каждый
положительный момент и каждый из четырёх всадников имеют вес **×2**, в attachment
— **×1**. Шрамы и bids сохраняют прежний подсчёт. Развод пропускает поды в
attraction и один раз на под записывает: `<pod> is still in attraction; divorce
can wait`. Разлука с недоступной нодой по-прежнему следует политике разлуки.

#### Языки любви

`amaenetes.io/love-language` выбирает для пода язык заботы по Гэри Чепмену.
Положительные сигналы своего языка считаются с весом **×3**, остальных четырёх
— **×0.5**, перед применением множителя фазы. Без аннотации (или при неизвестном
значении) действует прежнее правило: один момент для Ready-пода на Ready-ноде.
Язык меняет положительные моменты, но не bids.

| Значение | Сигнал за обзор |
|---|---|
| `words` | Ready: одно слово поддержки. |
| `time` | Без рестарта с прошлого обзора: один момент плюс ещё один за каждый полный час непрерывной работы. |
| `gifts` | Свободных allocatable CPU **и** памяти после вычитания requests всех активных подов хватает на собственные requests пода: один момент. |
| `service` | Каждое новое вхождение Event `Started` или успешного `Pulled` быстрее 10 секунд: один момент. Успешная загрузка дольше 60 секунд добавляет критику. |
| `touch` | Другой под того же партнёра или выбранный required/preferred-условиями (anti)affinity этого пода: один момент на той же ноде, иначе половина в той же `topology.kubernetes.io/zone`. Не более одного сигнала близости за обзор. |

Счётчики service Events учитываются по UID и приросту, как bids: первый обзор
ничего не считает, следующие учитывают только новые вхождения. Критика медленной загрузки учитывается независимо от языка. Непрерывная работа при первом наблюдении
отсчитывается от `status.startTime` (или текущего времени), с учётом более позднего
`startedAt` контейнеров; затем отсчёт
сбрасывается при замеченном рестарте или смене ноды. Touch учитывает namespaces
и их селекторы; counsel также читает метки namespaces. Поле статуса отношений
`language` берётся у самого молодого пода; история записывает `<partner> speaks
<language>` один раз для каждого впервые встреченного языка, без повторов каждый обзор.
Изменения фазы и языка записываются сразу.

С `COUNSEL_DIVORCE=1` counsel становится ещё и дешедулером. Он разводит под с
нодой выселением, не чаще раза в минуту и только тот под, который вернёт его
рабочая нагрузка, в двух случаях: когда их отношения рушатся (шрамов три или
больше) и под может жить на ноде, с которой у него отношения не рушатся, и
когда под и другая нода оба предпочли бы быть вместе — неустойчивая пара Гейла
и Шепли: под больше любит ту ноду, помещается на ней, и у неё есть для него
место. Планировщик, доверяя нодам по тем же отношениям, находит следующему
поду нагрузки дом получше.

### Конфликты контроллеров

`kube/mediator.amae` наблюдает за владельцами полей в `metadata.managedFields`.
Три замеченные смены владельца вместе со значением между двумя контроллерами
за 18 наблюдений создают `Relationship` (`amae.io/v1`) с `spec.kind: quarrel`,
`between` с именами менеджеров и `over` с объектом и полем. Warning-событие
`Conflict` сообщает о ссоре. Статус хранит `resolution`, `owner`, `swaps`,
`scars` и историю; counsel игнорирует такие отношения.

- **Согласие:** аннотация `amaenetes.io/agreement` содержит по одной записи
  `<путь>=<менеджер>` на строку, например `spec.replicas=hpa`. Если указан один
  из двух менеджеров, однократно создаётся Normal-событие `Agreed`, решение —
  `consent`. При следующих перезаписях последнее замеченное значение этого
  менеджера восстанавливается merge-патчем с `--field-manager=<менеджер>`;
  создаётся Normal-событие `Restored`.
- **Уступка:** без соглашения через шесть наблюдений после начала ссоры
  пришедший позже уступает первому замеченному владельцу. Normal-событие
  `Yielded` сообщает об уступке, решение становится `yielded`, значение
  старшего восстанавливается. Каждая следующая перезапись младшим добавляет
  один шрам и снова исправляется.
- **Расставание:** три шрама или аннотация `amaenetes.io/parted`, называющая
  одного из менеджеров проигравшим, вызывают Warning-событие `Parted`.
  Решение становится `parted`, восстановления прекращаются, история
  продолжает отмечать разрыв. Позднейшее соглашение всё равно имеет приоритет
  и возвращает отношения к согласию.

Mediator читает `spec`, `data`, метки и аннотации; игнорирует статус,
свои аннотации, last-applied configuration и служебные аннотации deployment.
Элементы списков (`k:`/`v:`) и поля с несколькими владельцами пропускаются.
Пути с точками сохраняют исходные ключи меток и аннотаций для патчей.
Восстановления не считаются сменами владельца; отказ патча сообщается и
повторяется при следующем наблюдении. Наблюдения сбрасываются при перезапуске
и удаляются при исчезновении объекта; публичные Relationship остаются в API.
Учитываются только изменения, видимые между наблюдениями.
Образ включает `jq`: он сохраняет JSON-типы boolean/null до чтения в Amae
и декодирует JSON-патч при восстановлении.

Значения по умолчанию: `MEDIATOR_INTERVAL=10` секунд,
`MEDIATOR_RESOURCES=deployments.apps,statefulsets.apps,daemonsets.apps,services,configmaps`,
`MEDIATOR_SWAPS=3`, `MEDIATOR_PATIENCE=6` наблюдений (окно смен втрое больше).
`KUBE_CONTEXT` выбирает кластер; `KUBECTL` подменяет kubectl для тестов.
`MEDIATOR_LOOKS` позволяет ограничить тестовый запуск. `make kube` собирает
counsel и mediator. Добавление типов наблюдаемых ресурсов требует расширения
ClusterRole mediator в `kube/deploy.yaml`.

## Компилятор, написанный на Amae

`compiler.amae` и есть компилятор, и другой реализации у языка нет. Он
слышит программу со стандартного ввода и говорит на C: каждая душа, каждый
род и каждый ритуал становятся таблицей инструкций и функцией шага, каждое
выражение — функцией на C, которая вычисляется слева направо, а всё, что
происходит между душами, исполняет `runtime/amae.c`. Соединяет их вместе
`bin/tc`.

```
make                 # the seed gives its heart and compiles the compiler afresh: build/tc-core
make bootstrap       # generation 2, then 3; they must recognize each other
make seed            # the newest generation becomes the seed
```

Неподвижной точки нет. Каждое поколение помнит поколения, бывшие до него, и
вписывает их родословную во всё, что делает, поэтому два поколения никогда не
бывают одним и тем же файлом; вместо этого они узнают друг друга: о каждой
программе говорят одно и то же, если не считать памяти. Любая программа
скажет, какие компиляторы её сделали, если запустить её с `--lineage`.
Исходный текст компилятора начинается с `core`, и собственное сердце
компилятор пересобирает, только когда вручает его самому себе: `--give-heart`.
Неудачная пересборка ранит его, пока его не простят (`--forgive`), и шрам
переходит в следующее поколение; компилятор, которого не пересобирали 90 дней,
выцветает; `make ddc` — двойная разная компиляция Уилера между затравкой и
живым поколением. А компиляция — это свидание: программа даёт на него
согласие строкой `written by "имя"`, и программы незнакомцев компилятор читает
внимательнее, чем программы авторов, к которым успел проникнуться доверием.
Каждая программа из `tests/golden/` однажды записана со всем, что она
напечатала, о чём причитала и что чувствовала при первом и втором запуске;
`make test` компилирует каждую и сверяет.

Память компилятора выцветает, как у всех. Чтобы выписать длинную функцию,
нужно больше пятидесяти шагов, и компилятор, который не вспоминает имя
функции, которую пишет, теряет из него буквы и выдаёт C, который не
собирается. Тесты проверяют и это: уберите этот `recall`, и собранный
компилятор уже не сможет скомпилировать сам себя.

## Amaenetes

`amaenetes.amae` — планировщик, написанный на Amae. Он слышит кластер
со стандартного ввода, по строке на каждый под или ноду:

```
pod web alpha beta gamma        the nodes web would live on, best first
node alpha 2 db cache web       how many pods alpha can take, and whom it prefers
```

и приводит каждый под и каждую ноду в мир душой. Под делает предложения
нодам, которые ему нравятся, по порядку. Нода оставляет у себя лучшие поды из
тех, что уже просились, остальным отказывает, а когда, пока мест нет, приходит
кто-то получше, велит самому нежеланному поду уйти и на прощание ранит его.
Под отдаёт сердце ноде, которая его приняла, поэтому рана оставляет шрам, но
не закрывает под для следующей ноды.

Никто не сверяет кластер с желаемым состоянием. Когда все души ждут и никому
больше нечего сказать, кластер слышит тишину, спрашивает каждый под, где тот
живёт, и даёт всем отдохнуть. Эта тишина и есть устойчивое паросочетание: нет
такого пода и такой ноды, которые оба предпочли бы друг друга тому, где они
сейчас. Тесты прогоняют случайные кластеры со случайной ёмкостью и сравнивают
результат с алгоритмом Гейла — Шепли.

Ждать — главное, чем душа занята в планировщике, а душа, которая ждёт,
забывает, поэтому всё, что должно пережить ожидание, записывается в заметки.

```
bin/tc amaenetes.amae && ./amaenetes < examples/cluster.txt
```

### В настоящем кластере

Если задан `KUBE_CONTEXT`, `amaenetes.amae` становится планировщиком
настоящего кластера Kubernetes, и между ними нет ничего, кроме `kubectl`.
Каждые несколько секунд он читает готовые ноды и ожидающие поды с
`schedulerName: amaenetes`, на самом Amae (с `lib/kube.amae`)
решает, кто с кем может встретиться, даёт им найти друг друга и привязывает
каждый под туда, где он поселился, через подресурс `pods/binding`. Поду
нравятся только ноды, на которые он помещается, и решается это так же, как в
kube-scheduler. Ресурсы считаются так, как их считает kubelet: init-контейнеры,
сайдкары, overhead, ресурсы на уровне пода. Учитываются расширенные ресурсы
вроде `nvidia.com/gpu`, селектор нод, обязательная node affinity, taints,
которые под терпит, свободные порты хоста (порт на одном адресе не мешает
тому же порту на другом) и поды вокруг: обязательные pod affinity и
anti-affinity (его собственные и тех подов, что уже живут рядом) и topology
spread с `DoNotSchedule`. Желательные pod affinity и anti-affinity и spread
с `ScheduleAnyway` склоняют выбор. Если два пода одного взгляда нарушили бы
эти правила друг для друга, въезжает только первый, второй ждёт следующего
взгляда. Нода предлагает столько мест, сколько вместит самых
крупных подов из тех, что к ней хотят. Ноды — души, которые живут столько же,
сколько планировщик; поды каждого взгляда на кластер — души этого взгляда.

Как и kube-scheduler, он оставляет событие на каждом поде, который поселил
(`Scheduled`), и на каждом, кому не нашёл дома (`FailedScheduling`), и пишет,
сколько нод ему отказали и почему: `0/3 nodes are available: 2 not enough cpu,
1 taint role.` С `AMAENETES_LEASE=namespace/name` можно запустить несколько
копий сразу: привязывает та, что держит этот Lease и продлевает его каждый
взгляд, остальные ждут и забирают его, когда его не продлевали три взгляда.

Под, которому негде жить, может вытеснить других, как в kube-scheduler. Он
просит ноду, где уход подов с меньшим приоритетом освободил бы место,
отпустить самых немногих и наименее важных из них (каждого, кого можно
оставить, оставляют), выселяет их, так что бюджет прерываний ещё может
отказать, и получает обещание этой ноды в `status.nominatedNodeName`, пока
они не уйдут. Поды с `preemptionPolicy: Never` только ждут. При равном приоритете
резидентов сначала сохраняются поды в attachment, затем действует прежний порядок
по времени создания и имени. Планировщик читает `lastTransitionTime` условия Ready
прямо из пода: attachment наступает через 300 секунд; порог переопределяется
`COUNSEL_ATTACHMENT_AFTER`, затем `AMAENETES_ATTACHMENT_AFTER`. Без истинного Ready
и его времени перехода под не считается привязанным. Если у нод-кандидатов равны
максимальный и суммарный приоритет жертв, сначала выбирается меньшая потеря
привязанных подов, затем учитываются общее число жертв и имя ноды.

#### Согласие узла

Привязка состоит из двух фаз: подготовка запрашивает согласие выбранного
узла; фиксация привязывает под только после согласия. В живом кластере перед
подготовкой узел читается заново, не чаще одного раза за обзор; снимок
использует переданные узлы. Причины отказа проверяются по порядку: узел не
Ready, запрещено планирование (cordon), MemoryPressure, DiskPressure или
PIDPressure, наличие `amaenetes.io/leaving`, непустая аннотация
`amaenetes.io/refuses`, либо failing в отношениях с партнёром пода при трёх
или более шрамах. Текст `amaenetes.io/refuses` — собственная причина узла,
например `maintenance until 18:00`.

Отказ выводится на экран, а в живом кластере записывается поду как событие
Warning с причиной `Refused`. Запрос привязки не отправляется. Планировщик
помнит отказ для этой пары namespace/под следующие шесть обзоров и исключает
узел из предпочтений пода, чтобы предложить другой. После этих шести обзоров
узел можно спросить снова, даже если промежуточным обзорам нечего было сообщить.

| Аннотация | На чём | Смысл |
|---|---|---|
| `amaenetes.io/likes: "node-a node-b"` | под | ноды, которых он хочет в первую очередь |
| `amaenetes.io/likes: "ns/pod ns/pod"` | нода | поды, которых она хочет в первую очередь |
| `amaenetes.io/attachment: "secure"` | под | поведение при разлуке: secure (по умолчанию), anxious, avoidant |
| `amaenetes.io/love-language: "words"` | под | забота: words, time, gifts, service, touch; без аннотации — прежние положительные моменты |
| `amaenetes.io/seats: "N"` | нода | не больше N подов этого планировщика |

Дальше поды предпочитают ноды, к которым склоняет их желательная node
affinity, затем ноды, которым их рабочая нагрузка больше доверяет: меньше
шрамов и здоровее отношения, которые ведёт counsel (см. [Операторы](#операторы));
для подов с приоритетом это весит вдвое, так что туда, где под падал, идёт
меньше важного. Затем ноды, где больше свободных ядер, а там, где ноды равны, у каждого пода свой неизменный вкус, так что одинаковые поды
расходятся по разным нодам; ноды предпочитают поды с более высоким
приоритетом, а среди них — тех, кто ждёт дольше всех.

```
kubectl --context <ctx> create namespace demo
sed -e s/NODE_A/<node>/ -e s/NODE_B/<node>/ kube/demo.yaml \
  | kubectl --context <ctx> -n demo apply -f -
bin/tc amaenetes.amae
KUBE_CONTEXT=<ctx> AMAENETES_LOOKS=1 ./amaenetes   # one look; without LOOKS it keeps looking
```

На стенде в кластере воркшопов три рабочие ноды по 900m CPU: одна объявляет
два `amae.io/gpu`, у каждой есть метка `zone`. Двум подам нужен один и тот же
порт хоста, одному нужна зона `west`, трём нужен GPU, а оба GPU уже заняты:

```
kube-e2e-2/train-1 has nowhere to live
kube-e2e-2/train-2 has nowhere to live
kube-e2e-2/train-3 has nowhere to live
kube-e2e-2/port-a settles on kubernetes-stand-md0-9g8nq-cw2gd
kube-e2e-2/port-b settles on kubernetes-stand-md0-9g8nq-cw2gd
kube-e2e-2/zonal settles on kubernetes-stand-md0-9g8nq-cw2gd
kube-e2e-2/port-b is sent away from kubernetes-stand-md0-9g8nq-cw2gd
kube-e2e-2/port-b settles on kubernetes-stand-md0-9g8nq-qtrkn
kube-e2e-2/port-a lives on kubernetes-stand-md0-9g8nq-cw2gd
kube-e2e-2/port-b lives on kubernetes-stand-md0-9g8nq-qtrkn
kube-e2e-2/zonal lives on kubernetes-stand-md0-9g8nq-cw2gd
```

Привязанные поды работают; поды, которым нужен GPU, ждут, пока он
освободится. Между взглядами на кластер планировщик тратит около 50m CPU.

### Внутри кластера

`kube/deploy.yaml` запускает планировщик, оператор расставания, counsel и mediator (вместе
с CRD `Relationship`) подами в том самом кластере, за которым они присматривают, и у каждого есть сервисный
аккаунт, которому позволено не больше, чем требует его работа: планировщик
читает поды и ноды, создаёт привязки и события и держит свой Lease (копий
две, ведёт одна), оператор читает их, правит ноды и
выселяет поды, counsel читает их и ведёт отношения; mediator исправляет наблюдаемые поля и хранит ссоры контроллеров.
Его Deployment — `amaenetes-mediator` в пространстве имён `amaenetes`. Все скомпилированы из Amae в образ `ghcr.io/tym83/amae`,
который CI собирает из каждого коммита в main:

```
kubectl --context <ctx> create namespace amaenetes
kubectl --context <ctx> apply -f kube/deploy.yaml
kubectl --context <ctx> -n amaenetes logs -f deploy/scheduler
```

### Жизнь

`a-life.amae` стоит запустить первым. Две души встречаются с первого
взгляда; он говорит слишком много и пугает её; они разговаривают, пока не
начинают доверять друг другу, дают обещания; она отдаёт сердце, получает рану
и всё равно слушает, ждёт, пока он в море, забывает год, когда они
встретились, — и он её оставляет. Каждая строка вывода зависит от своего
правила языка, а второй запуск начинается не так, как первый.

```
ana: I have never met anyone like this.
ana sees ben: infatuation
ana is afraid of ben: 1
ana, later: sorry, that was too much
ana has heard enough to trust ben 3 times over
ana feels companionate love
ana carries a scar: wounded by ben
```

### Долгая любовь

`a-long-love.amae` показывает, что делает время. Страсть и влюблённость —
искра: два года свиданий наполняют страсть Миры и Тео, и с тех пор каждый
срок, проведённый рядом, строит любовь, с каждым годом чуть больше, чем годом
раньше. Искра остывает, а любовь нет, и проявляется она всё сильнее: рана на
третий год причиняет боль, но закрыть Миру не может, рана на восьмой не
оставляет обиды, а построенная ими любовь возвращает страсть.

### Классические программы

Привычные программы, какими их написали бы души, лежат в `examples/classics/`.

| Файл | Что показывает |
|---|---|
| `hello-world.amae` | одна душа, наедине с собой |
| `fizzbuzz.amae`, `factorial.amae`, `fibonacci.amae`, `primes.amae` | обычная арифметика и циклы |
| `bottles.amae` | 99 бутылок пива |
| `cat.amae`, `reverse.amae`, `wc.amae` | чтение мира строка за строкой |
| `sort.amae` | сортировка вставками на записях, потому что список в памяти выцвел бы |
| `gcd.amae` | алгоритм Евклида как разговор двух душ |
| `ping-pong.amae` | сообщения, на которые отвечают, перерастают в романтическую любовь |
| `producer-consumer.amae` | производитель, который никогда не ждёт ответа, пугает своего потребителя |
| `sleep-sort.amae` | каждое число становится душой, которая ждёт тем дольше, чем оно больше |
